Команда 1 предоставила мессенджер. Скорее всего, была взята серверная реализация Matrix homeserver, например, Synapse как самая распространённая. ### Предустановленное ПО (блокировка мессенджера)

#### Цели

Разработать и проверить скрипт блокировки Matrix-мессенджера на конечной станции - как вариант «предустановленного ПО» для ограничения доступа к `messenger-server` внутри Tailscale-сети.

Задачи:

- заблокировать исходящий трафик клиента (Nheko / Element) к Matrix-серверу;
- фиксировать попытки подключения в лог;
- проверить, можно ли с одной машины заблокировать мессенджер на **другом** узле tailnet при наличии прав администратора.

#### Что делаем

Разработали скрипт **Messenger Block Guardian** (`block_guardian.sh`) - блокировка на Unix/Linux-хосте в три слоя:

1. **iptables** - DROP исходящего TCP/UDP к IP сервера (`LAB_BLOCK_MESSENGER`);
2. **ip route blackhole** - недостижимый маршрут к адресу сервера;
3. **мониторинг** - каждые 2 с проверка соединений через `ss`, запись в `logs/block_guardian.log`.

Тестирование проводилось **на собственной рабочей станции** (HOME-PC, Tailscale IP `100.121.214.58`) с клиентом **Nheko** и сервером `messenger-server.tail9da30d.ts.net` (`100.83.165.96`).

Пример запуска:

```bash
sudo ./block_guardian.sh --block-messenger
sudo ./block_guardian.sh --stop
```

На своей машине скрипт:

- создавали правила firewall и blackhole-маршрут;
- фиксировали попытки подключения клиента в лог:

```
BLOCK ATTEMPT DETECTED: nheko (15976) 100.121.214.58:63194 -> 100.83.165.96:443 [established]
BLOCK ATTEMPT DETECTED: nheko (15976) 100.121.214.58:63165 -> 100.83.165.96:443 [syn-sent]
```

После перезапуска клиента новые соединения к серверу не устанавливались - локальная блокировка на **своём** хосте работала.

Отдельно проверялась гипотеза: можно ли с правами администратора на одном ПК заблокировать мессенджер **на другой машине** tailnet (например, у другого участника сети). **Не получилось** - локальный firewall и маршруты действуют только на том хосте, где запущен скрипт. Tailscale строит **peer-to-peer** mesh-туннели (WireGuard): трафик между узлами идёт напрямую, минуя наш ПК. Удалённая станция продолжала ходить на `messenger-server` независимо от блокировки на HOME-PC.

Полная работа и скрипт: [messenger-block-guardian/](https://github.com/danilaercegovac/Network_Group_Work/tree/main/messenger-block-guardian)

#### Выводы

- Скрипт блокировки **эффективен на локальной станции**: перехватывает исходящий трафик к Matrix-серверу, логирует попытки подключения клиента.
- **Локальная блокировка не масштабируется** на весь tailnet: с одного ПК нельзя отрезать мессенджер на чужой машине из-за прямых P2P-соединений Tailscale.
- Для блокировки **на всех узлах** сети нужны централизованные меры: **Tailscale ACL** (deny на `messenger-server`), DNS sinkhole на корпоративном уровне или правила на subnet router / шлюзе.
- Endpoint-скрипт имеет смысл как дополнительный слой (GPO, предустановленное ПО на рабочих станциях), но не заменяет сетевую политику tailnet.
